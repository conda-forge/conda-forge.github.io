# NVIDIA CUDA packages

This page is for people who wish to use conda environments to run CUDA-enabled software.
To build CUDA packages, see [Build NVIDIA CUDA packages](/docs/how-to/advanced/cuda/).

## CUDA prerequisites

You must have an NVIDIA GPU on your machine and you must install the CUDA drivers. The CUDA
driver _cannot_ be installed with conda and must be installed on your system using an
appropriate installation method. See the [CUDA documentation](https://docs.nvidia.com/cuda/)
for instructions on how to install the CUDA driver
([Linux](https://docs.nvidia.com/cuda/cuda-installation-guide-linux/index.html),
[Windows](https://docs.nvidia.com/cuda/cuda-installation-guide-microsoft-windows/index.html)).

Conda CUDA packages are installable even if no CUDA driver or NVIDIA GPU is available, but
they will not run properly. See [Installing CUDA packages without a
GPU](#cuda-without-a-gpu) for how to do this.

## Installing CUDA-enabled packages

You do not need to install the CUDA Toolkit yourself to use CUDA-enabled packages. They
depend on the CUDA libraries they need, and conda installs those as dependencies. For example,
to install PyTorch:

```bash
conda install -c conda-forge pytorch
```

If conda detects a CUDA driver (that is, the `__cuda` virtual package is available), it
selects the CUDA-enabled build. To choose the major version of CUDA, add the `cuda-version`
metapackage:

```bash
conda install -c conda-forge pytorch cuda-version=12
```

To require a CUDA-enabled build, match the build string:

```bash
conda install -c conda-forge "pytorch=*=cuda*"
```

### Installing CUDA packages without a GPU {#cuda-without-a-gpu}

All of the CUDA packages can be installed in an environment without a physical GPU or CUDA
driver, such as on an HPC login node (where the compute nodes have GPUs but no internet
access) or on free-tier CIs by setting the `CONDA_OVERRIDE_CUDA`/`CONDA_OVERRIDE_CUDA_ARCH`
environment variable to the desired CUDA version.

<Tabs groupId="synced-shell-tabs">
<TabItem label="bash" value="bash" default>

```bash
CONDA_OVERRIDE_CUDA="12.9" CONDA_OVERRIDE_CUDA_ARCH="10.0" conda install tensorflow -c conda-forge
```

</TabItem>
<TabItem label="cmd" value="cmd">

```batch
set CONDA_OVERRIDE_CUDA=12.9
set CONDA_OVERRIDE_CUDA_ARCH=10.0
conda install tensorflow -c conda-forge
```

</TabItem>
<TabItem label="PowerShell" value="powershell">

```powershell
$env:CONDA_OVERRIDE_CUDA = "12.9"
$env:CONDA_OVERRIDE_CUDA_ARCH = "10.0"
conda install tensorflow -c conda-forge
```

</TabItem>
</Tabs>

In `cmd` and PowerShell the variable stays set for the rest of the shell session.

Even if the package requires CUDA to run, this allows packaging and dependency resolution to
be tested in a CPU-only environment.

### Lock files and CUDA packages {#cuda-lock-files}

CUDA packages are less portable between machines than CPU-only packages. Besides the
platform (e.g. `linux-64`), a CUDA package may have multiple variants for `cuda-version`
(constrained by the `__cuda` virtual package, i.e. the CUDA driver) and for `cuda-arch`
(constrained by the `__cuda_arch` virtual package, i.e. the compute capability of the least
capable GPU). A lock file records exactly one variant of each package, chosen for the
virtual packages present when the lock file was solved. Furthermore, newer versions of a
package may drop support for older values of `cuda-version` and `cuda-arch`.

As a result, an environment locked on one machine may:

- not be installable on another machine, because that machine's driver is older than the
  locked `cuda-version` or its GPUs have a lower compute capability than the locked
  `cuda-arch`;
- install but have suboptimal performance, because the locked variant was not built for
  that machine's newer GPUs, or because no GPU was detected and a CPU-only variant was
  locked.

If your lock files need to work on more than one kind of machine, create multiple lock files
(or multiple locked environments) for the different situations you need to support, e.g. one
per minimum driver version and GPU generation. Declare the virtual packages explicitly
for each lock file instead of relying on whatever the solving machine happens to have.

Each of the examples below locks `kokkos` for `linux-64` twice: once for machines with a
CUDA 12 driver and Ampere (compute capability 8.0) or newer GPUs, and once for machines with
a CUDA 13 driver and Blackwell (compute capability 10.0) or newer GPUs.

<Tabs>
<TabItem label="conda" value="conda" default>

The `CONDA_OVERRIDE_CUDA` and `CONDA_OVERRIDE_CUDA_ARCH` environment variables described
[above](#cuda-without-a-gpu) set the virtual packages used when solving an environment.
Solve and export one explicit lock file per situation:

```bash
CONDA_OVERRIDE_CUDA="12.0" CONDA_OVERRIDE_CUDA_ARCH="8.0" \
  conda create -n cuda12-ampere -c conda-forge kokkos
conda export -n cuda12-ampere --format=explicit --file=cuda12-ampere.txt

CONDA_OVERRIDE_CUDA="13.0" CONDA_OVERRIDE_CUDA_ARCH="10.0" \
  conda create -n cuda13-blackwell -c conda-forge kokkos
conda export -n cuda13-blackwell --format=explicit --file=cuda13-blackwell.txt
```

</TabItem>
<TabItem label="conda-lock" value="conda-lock">

[conda-lock](https://github.com/conda/conda-lock) reads the virtual packages from a file
passed with `--virtual-package-spec`. This file replaces conda-lock's default virtual
packages, so it must also list any other virtual packages that your dependencies require,
such as `__glibc`. Otherwise, conda-lock may silently lock an old or CPU-only build. Create
one spec file and one lock file per situation:

```yaml title="environment.yml"
channels:
  - conda-forge
dependencies:
  - kokkos
```

```yaml title="virtual-packages-cuda12-ampere.yml"
subdirs:
  linux-64:
    packages:
      __glibc: "2.28"
      __cuda: "12.0"
      __cuda_arch: "8.0"
```

```yaml title="virtual-packages-cuda13-blackwell.yml"
subdirs:
  linux-64:
    packages:
      __glibc: "2.28"
      __cuda: "13.0"
      __cuda_arch: "10.0"
```

```bash
conda-lock -f environment.yml -p linux-64 \
  --virtual-package-spec virtual-packages-cuda12-ampere.yml \
  --lockfile cuda12-ampere.conda-lock.yml
conda-lock -f environment.yml -p linux-64 \
  --virtual-package-spec virtual-packages-cuda13-blackwell.yml \
  --lockfile cuda13-blackwell.conda-lock.yml
```

</TabItem>
<TabItem label="pixi" value="pixi">

```toml title="pixi.toml"
cuda12-ampere = ["cuda12-ampere"]
cuda13-blackwell = ["cuda13-blackwell"]
```

```bash

```

## Installing the CUDA Toolkit

The sections below are for developers who need the CUDA compiler, headers, or tools.
Most users do not need to install the full toolkit.

### Basic Installation

The easiest one-step solution to install the full CUDA Toolkit is to install the [`cuda`
metapackage](https://github.com/conda-forge/cuda-feedstock/) with this command:

```bash
conda install -c conda-forge cuda cuda-version=12.9
```

Let's break down this command. We are requesting the installation of two metapackages:
`cuda` and `cuda-version`.

The `cuda` metapackage pulls in all the components of the CUDA Toolkit (CTK) and is roughly
equivalent to installing the CUDA Toolkit with traditional system package managers like
`apt` or `yum` on Linux. Similarly to such package managers, the individual components may
also be installed independently.

The [`cuda-version` metapackage](
https://github.com/conda-forge/cuda-version-feedstock/blob/main/recipe/README.md )
is used to select the version of CUDA to install. This metapackage is important because
individual components of the CTK are typically versioned independently (the current versions
may be found in the [release notes](
https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html )). The
`cuda-version` metapackage provides a standard way to install the version of a specific CUDA
component corresponding to a given version of the CTK. This way, one never has to specify a
particular version of any CTK package; one just specifies the `cuda-version` desired,
then list packages needed and conda will take care of finding the right versions.
The above command will install all components of CUDA from the latest patch release
of the CUDA 12.x series.

:::note

The following CUDA components are not available as conda packages:

- Driver libraries, such as (but not limited to)
  - `libcuda`
  - `libnvidia-ml` library
  - GPUDirect Storage (GDS)
- Documentation and Samples
- Fabric Manager
- IMEX
- NVSwitch Configuration and Query (NSCQ)
- Nsight Systems

:::

### Installing individual components of the CUDA Toolkit

Rather than installing all of CUDA at once, users may instead install just the packages that
they need. For example, to install just `libcublas-dev` and `libcusparse-dev` one may run:

```bash
conda install -c conda-forge libcublas-dev libcusparse-dev cuda-version=13
```

The best way to get a current listing is to run:

```bash
conda install --dry-run -c conda-forge cuda cuda-version=13
```

For a complete listing of the packages that were originally created, see [this
issue](https://github.com/conda-forge/staged-recipes/issues/21382).

### Metapackages

For convenience, a number of additional metapackages are available:

- `cuda-runtime` / `cuda-libraries`: All CUDA runtime libraries needed to run a CUDA application
- `cuda-visual-tools`: GUIs for visualizing and profiling such as Nsight™ Compute
- `cuda-command-line-tools`: Command line tools for analyzing and profiling such as cupti, cuda-gdb, and Compute Sanitizer
- `cuda-tools`: All tools for analyzing and profiling, both GUI (includes cuda-visual-tools) and CLI (includes cuda-command-line-tools)

### Selecting ARM Device Variant

Many of NVIDIA's CUDA packages are built for both SBSA and Tegra devices. For CUDA 12.9,
Tegra devices are a separate ARM variant. To install packages built for CUDA 12.9 Tegra, add
the `arm-variant=*=tegra` package to your environment. For CUDA 13.0 and later, the
arm-variant package is no longer required. Tegra devices are no longer a separate
architecture from SBSA.

```bash
conda install -c conda-forge pytorch "arm-variant=*=tegra"
```

:::info

Support for Tegra builds on conda-forge is only available for CUDA 12.9 and later. This
means that only Orin (sm_87) and later devices are supported.

:::

## CUDA C++ Core Libraries (CCCL)

CCCL is a special case among CUDA packages. Due to 1) being header-only, 2) fast-moving, and 3) independently-evolving,
consumers may want a different (newer) version of CCCL than the
one corresponding to their CTK version. Instructions on how to install a suitable CCCL
package from conda can be found
[in the CCCL README](https://github.com/NVIDIA/cccl/?tab=readme-ov-file#conda).
See [this issue](https://github.com/conda-forge/cuda-cccl-impl-feedstock/issues/2)
for more information on the history of these packages.

## CUDA package naming conventions

CUDA libraries are split into separate packages with standard naming:

- The base package (e.g., `libcublas`) provides runtime shared libraries.
- The `*-dev` package includes headers, symlinks, and CMake files for compiling code that dynamically links the library.
- The `*-static` package includes the static library for static linking.
  For build files, users may also needed to install the `*-dev` packages.

For example, [libcublas](https://github.com/conda-forge/libcublas-feedstock) is available as `libcublas`, `libcublas-dev`, and `libcublas-static`.

## CUDA development metapackages

The above discussion of naming also applies to metapackages. For instance, the
`cuda-libraries` package contains all the runtime libraries, while `cuda-libraries-dev` also
includes dependencies on the corresponding `*-dev` packages. In addition, for the purposes
of development there are a few additional key metapackages:

- `cuda-compiler`: All packages required to compile a minimal CUDA program (one that does
  not require e.g. extra math libraries like cuBLAS or cuSPARSE).

## Compatibility between the `conda-forge` vs `nvidia` channels

Understanding the difference between the CUDA packages on the `conda-forge` and `nvidia`
channels requires a bit of history because of how the relationship has evolved over time. In
particular, how these channels may or may not coexist will depend on the versions of CUDA
that you need support for.

<details>
<summary>Pre-CUDA 12</summary>

Prior to CUDA 12, the only package available on `conda-forge` was the `cudatoolkit` package,
a community-maintained, monolithic package containing the entire repackaged CTK. During the
CUDA 11 release cycle, NVIDIA began developing a set of CUDA Toolkit packages in the
`nvidia` channel. Unlike the monolithic `conda-forge` package, the `nvidia` channel
distributed the CTK split into components such that each library was given its own package.
This package organization made it possible to install separate components independently and
better aligned the conda packaging ecosystem with other package managers, such as those for
Linux distributions. However, this organization introduced a number of changes that were at
times confusing -- such as the introduction of a `cuda-toolkit` (note the hyphen)
metapackage that installs a partially overlapping set of components to the original
`cudatoolkit` -- and at other times breaking, particularly in conda environments configured
to pull packages from both `conda-forge` and the `nvidia` channel. Therefore, in a CUDA 11
world the `conda-forge` and `nvidia` channels were difficult to use in the same environment
without some care.

</details>
<details>
<summary>CUDA 12.0-12.4</summary>

With the CUDA 12 release, NVIDIA contributed the new packaging structure to `conda-forge`,
introducing the CUDA Toolkit packages that existed on the `nvidia` channel as a replacement
for the old `cudatoolkit` package on `conda-forge`. This was done starting with CUDA 12.0 to
indicate the breaking nature of these changes compared to the prior CUDA 11.x packaging in
`conda-forge`. These packages became the standard mechanism for delivering CUDA conda
packages. Due to the scale of the reorganization, the CUDA 12.0, 12.1, and 12.2 releases
also involved numerous additional fixes to the packaging structure to better integrate them
in the conda ecosystem. Due to the number of such changes that were required and the focus
on improving the quality of these installations, no corresponding updates were provided for
packages on the `nvidia` channel during this time period. While the `conda-forge` and
`nvidia` channel package lists were the same (i.e. the same packages existed in both places
with the same core contents like libraries and headers), the `nvidia` channel did not
include many of the incremental fixes made on `conda-forge` to improve things like symlinks,
static library handling, proper package constraints, etc. As a result, `nvidia` and
`conda-forge` CUDA packages remained incompatible from CUDA 12.0-12.4.

</details>
<details>
<summary>CUDA 12.5+</summary>

With CUDA 12.5, the `nvidia` channel was fully aligned with `conda-forge`. Packages on both
channels are identical, ensuring safe coexistence of the two channels within the same conda
environment.

Additionally [Anaconda has incorporated compatible CUDA 12 packages in its `defaults` channel]( https://www.anaconda.com/blog/anaconda-accelerates-ai-development-and-deployment-with-nvidia-cuda-toolkit).

Going forward, CUDA packages on the `conda-forge` and `nvidia` channels should be expected
to remain compatible.

</details>
<details>
<summary>CUDA 13.4+</summary>

CUDA 13.3, is the last CTK release to the `nvidia` channel.

Going forward, CUDA packages should be retrieved from `conda-forge`.
</details>

## Compiling CUDA code in your environment

Beginning with CUDA 12.0, a full suite of CUDA packages is provided in conda-forge, including
various metapackages that group components together. To compile CUDA host or device code in
your environment, see [CUDA package naming conventions](#cuda-package-naming-conventions) and
[CUDA development metapackages](#cuda-development-metapackages).

## Troubleshooting CUDA

### What if I see an error saying `__cuda` is too old?

The `__cuda` virtual package is used by `conda` to represent the maximum CUDA version fully
supported by the available CUDA driver. See the [conda docs on virtual
packages](https://conda.io/projects/conda/en/latest/user-guide/tasks/manage-virtual.html)
for more information.

To update the `__cuda` virtual package, you must install a newer driver:

- [Linux instructions](https://docs.nvidia.com/cuda/cuda-installation-guide-linux/index.html#driver-installation)
- [Windows instructions](https://docs.nvidia.com/cuda/cuda-installation-guide-microsoft-windows/index.html#installing-cuda-development-tools)

If conda has incorrectly identified the CUDA driver, you can override by setting the
`CONDA_OVERRIDE_CUDA` environment variable to a version number like `"12.5"` or `""` to
indicate that no CUDA driver is detected.

### What if I see an error saying that `__cuda_arch` is missing?

For example, conda may report:

```bash
__cuda_arch >=8.9, for which no candidates were found
```
or
```bash
__cuda_arch >=12.1 *, which is missing on the system
```

The `__cuda_arch` virtual package is used by `conda` to represent the minimum compute
capability of the CUDA devices available on your system.

To provide or update the `__cuda_arch` virtual package:

- If you use conda, install the `nvidia-virtual-packages` plugin into your `base`
  environment with `conda install -n base -c conda-forge nvidia-virtual-packages`.
- If you use another package manager (e.g., pixi or mamba), try updating it to a newer
  version which implements `__cuda_arch`
- Use a CUDA device with a higher compute capability

If conda has incorrectly identified the least capable device or if you want to raise the minimum
supported compute capability of your environment, you can override by setting the
`CONDA_OVERRIDE_CUDA_ARCH` environment variable to a version number like `"10.0"` or `""` to
indicate that no devices are detected.
